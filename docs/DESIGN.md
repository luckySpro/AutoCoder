## 1. 要解决的问题

一台电脑上往往同时装了 Claude Code、Codex、Cursor 等多个 AI 开发工具，但它们彼此不知道对方的存在：

- 同一个项目只能"选一个工具干活"，其余工具闲置；
- 想并行用多个工具时，它们会在同一个工作目录里互相覆盖文件；
- 每个工具的进度散落在各自的对话里，没有统一的地方看"项目做到哪了"。

AutoCoder 的目标：**把本机的多个开发工具组织成一个小团队**——一个负责架构与项目管理，其余负责开发、前端、测试、评审——并用 **git** 作为团队唯一的协作介质。

所有工具都以**命令行（CLI）方式**接入：由 AutoCoder 统一派发、统一管理进程、统一计量 token。IDE 类工具使用其 CLI 版本（例如 Cursor 使用 Cursor Agent CLI）。

## 2. 核心概念

| 概念 | 说明 | 在 git 中的体现 |
|---|---|---|
| 工具 (Tool) | 本机安装的一个开发工具，来自工具清单 | — |
| 角色 (Role) | 工具在项目中的职责 | `.autocoder/project.yaml` 中的 `roles` |
| 项目 (Project) | 一个被 AutoCoder 管理的 git 仓库 | 仓库本身 + `.autocoder/` 目录 |
| 任务 (Task) | 项目管理拆分出的最小工作单元，构成依赖图 | 一个分支 `ac/<id>-<slug>` + 一个 worktree |
| 汇报 (Report) | 任务执行者向项目管理反馈的进度 | 编排器观察到的事实（进程、改动、验证结果）+ 编排器写的提交 + `.autocoder/reports/<id>.md` |
| 集成 (Integration) | 项目管理把完成的任务拼接起来 | 合并到 `ac/integration`，验证后合并到主分支 |
| 计量 (Usage) | 每次调用工具消耗的 token | `.autocoder/usage/*.jsonl`（不提交，见 §7） |

## 3. 角色定义与分配

### 3.1 角色

| 角色 | id | 职责 |
|---|---|---|
| 架构与项目管理 | `lead` | 架构设计；把需求拆成功能任务与视觉任务；生成任务依赖图并派发；接收汇报；按依赖顺序集成分支；处理受阻任务 |
| 开发 | `developer` | 领取功能任务，在自己的分支和 worktree 中实现、提交、汇报 |
| 前端/视觉 | `frontend` | 领取界面、交互、视觉任务 |
| 测试 | `tester` | 为已完成的任务编写测试、执行回归，把质量结果汇报给项目管理 |
| 评审 | `reviewer` | 合并前审查任务分支的 diff，给出通过/修改意见 |

### 3.2 默认分配规则（已实现：`internal/roles`）

0. 只有已安装、且清单中有非交互调用模板（`headless`）的 CLI 工具参与分配。
1. **只有一个可用工具**：它承担全部角色，AutoCoder 退化为"单工具 + git 任务管理"。
2. **多个工具**：**能力评分最高**的担任 `lead`。
3. 其余工具按 **擅长方向匹配 (+100) + 能力评分** 依次认领 开发 → 前端/视觉 → 测试 → 评审。
4. 工具不够分时：评审回落给 `lead`（它本来就负责合并把关）；其余角色由最匹配的工具兼任。
5. 工具多于角色时，多出来的工具都作为额外的开发者，并行领取任务。
6. 用户可以在界面上任意调整，保存后覆盖推荐值；`lead` 只能有一个。

以本机装有 Claude Code、Codex、Cursor Agent CLI 为例，默认分配为：

| 工具 | 角色 |
|---|---|
| Claude Code | 架构与项目管理、评审 |
| Codex CLI | 开发、测试 |
| Cursor Agent CLI | 前端/视觉 |

"能力评分"目前是清单中人工给出的静态值；后续可以结合计量数据（§7）做动态调整：每个工具在本项目中任务的通过率（测试是否通过、评审是否打回）与单位任务 token 消耗。

## 4. 工具清单与启动检测（已实现：`internal/toolscan`）

### 4.1 清单

- 内置清单：`internal/toolscan/tools.yaml`，只收录 CLI 工具：Claude Code、Codex CLI、Cursor Agent CLI、Gemini CLI、Qwen Code、GitHub Copilot CLI、OpenCode、Aider。
- 用户清单：`~/.autocoder/tools.yaml`，按 `id` 覆盖或追加；`disabled: true` 可排除不想参与协同的工具。
- **用户不需要编辑这个文件。** 工具清单页可以添加、编辑、停用/启用、删除（内置工具则是恢复默认）、导入和导出，保存后立即重新检测。文件只是界面的存储格式：写入时先写临时文件再原子替换，并保留 `.bak`；每个条目都会校验（id 格式、命令名不含路径分隔符、headless 模板必须含 `{prompt}`、能力评分 0–100、擅长方向取值）。
- 每个工具标注来源：`builtin`（内置未改）、`modified`（覆盖了内置）、`custom`（用户新增）。

对应接口（只接受本机访问，见 §8）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/tools` | 合并后的清单 + 检测结果 |
| PUT | `/api/tools/{id}` | 新增或修改一个工具 |
| DELETE | `/api/tools/{id}` | 删除自定义工具 / 内置工具恢复默认 |
| GET | `/api/tools/export` | 下载用户清单 YAML |
| POST | `/api/tools/import` | 导入 YAML，按 id 合并 |

每个条目的关键字段：

```yaml
- id: codex
  name: Codex CLI
  commands: [codex]         # 在 PATH 中依次查找
  paths: { darwin: [...] }  # 可选：按系统的额外路径（不在 PATH 中的安装位置）
  version_args: ["--version"]
  headless: ["exec", "{prompt}"]   # 非交互调用模板，编排器用它派发任务
  usage_args: ["--json"]           # 让工具输出带 token 用量的结构化结果（见 §7）
  capability: 90
  strengths: [coding, architecture, testing]
```

### 4.2 检测流程

启动时（`autocoder` 或 `autocoder tools`）：

1. 读取内置清单并合并用户清单；
2. 并发检测每个工具：先查 PATH，再查平台路径；
3. 找到可执行文件后以 5 秒超时执行 `version_args` 取版本号；
4. 结果按"已安装优先、能力评分降序"排序，缓存在服务中，界面"重新检测"可刷新；
5. 根据结果给出默认角色分配。

检测只做 `which` + `--version`，不读取任何工具的凭据或配置。

## 5. 以 git 为核心的项目管理

### 5.1 项目即仓库

创建项目有三种来源：新建仓库（`git init`）、克隆远程（`git clone`）、接管已有目录。

**参照 Claude Code 的添加方式**：本机已经绑定 git 身份并用 `gh auth login` 登录过 GitHub 时，"添加项目"直接列出账号下的仓库，搜索、点选即可克隆，不用复制地址：

- `GET /api/git/identity`：读 `git config --global user.name / user.email` 和 `gh auth status`（只解析登录账号与主机，不读取 token）。
- `GET /api/git/repos`：`gh repo list --json …`，按最近更新排序；未安装或未登录 `gh` 时返回 412，界面提示登录命令并退回"粘贴地址"。
- `GET /api/git/local`：扫描 `~/code`、`~/projects`、`~/src`、`~/dev`、`~/workspace` 下已有的 git 仓库，用于"接管本机目录"。
- 新建项目可选同时用 `gh repo create` 建远程仓库。对话框底部始终预览将执行的命令。

创建时：

```text
<repo>/
├── .autocoder/
│   ├── project.yaml     # 项目元数据、角色分配快照、分支约定
│   ├── plan.md          # lead 产出的架构设计与拆分说明
│   ├── tasks/T1.yaml    # 每个任务一个文件：标题、角色、负责工具、依赖、验收标准
│   └── reports/T1.md    # 每个任务的汇报记录（追加写）
└── ...项目代码
```

然后 `git commit` 初始化，并从主分支创建集成分支 `ac/integration`。所有项目状态都在仓库里，**换一台机器 clone 下来状态仍在**，也能直接用 `git log` 审计谁做了什么。

### 5.2 分支与工作区

- 每个任务一个分支：`ac/<task-id>-<slug>`，从 `ac/integration` 的当前位置切出（这样能拿到已合并的依赖任务成果）。
- 每个任务一个 **git worktree**：`../.ac-worktrees/<project>/<task-id>`。多个工具同时工作时各自在独立目录里改文件，互不覆盖。
- 主分支只接受 `lead` 从 `ac/integration` 发起的合并；工具不直接提交到主分支或集成分支。
- 如果配置了远程仓库，任务分支可推送并创建 PR，让人也能在 GitHub 上评审（可选）。

### 5.3 任务文件示例

```yaml
# .autocoder/tasks/T3.yaml
id: T3
title: 订单 API 与状态机
kind: feature          # feature | ui | test | infra
role: developer
assignee: codex
depends_on: [T1]
branch: ac/T3-order-api
acceptance:
  - 订单状态：待支付 → 已支付 → 已发货 → 完成 / 取消
  - go test ./internal/order/... 通过
status: running
```

## 6. 任务执行：分配、过程反馈与交付

总原则：**以看得见的事实为准，不依赖工具自述。** 工具只负责在自己的 worktree 里改代码；提交、状态推进、验证、合并和交付全部由编排器完成。判断依据是进程状态、事件流、工作区改动、验证命令结果和 git 历史。这样即使某个工具没按约定汇报，整个流程也不会断。

### 6.1 从需求到计划

1. 用户在界面里写需求，保存为 `.autocoder/requests/R1.md`。
2. lead 在主分支的只读 worktree 中分析仓库，产出 `plan.md`（架构说明，给人看）和 `plan.json`（任务清单，给程序用）：

```json
{
  "questions": [],
  "test_command": "go test ./...",
  "setup_command": "npm ci --prefix web",
  "tasks": [
    {
      "id": "T3", "title": "订单 API 与状态机", "kind": "feature", "role": "developer",
      "depends_on": ["T1"],
      "scope": ["internal/order/**", "internal/server/order*.go"],
      "acceptance": ["订单状态：待支付 → 已支付 → 已发货 → 完成 / 取消"],
      "verify": ["go test ./internal/order/..."]
    }
  ]
}
```

3. 编排器校验计划，不通过时把错误原样交回 lead 重写，最多 2 次，仍不通过就转给用户：
   - JSON 格式正确，任务 id 唯一，依赖都存在且没有环；
   - 每个任务的角色都有工具承担；
   - 每个任务至少一条验收标准，且有可执行的 `verify` 命令，或明确标注"人工验收"；
   - **并行任务的 `scope` 不能重叠**：重叠时自动在两者之间加依赖、改为先后执行，避免合并冲突；
   - 任务数量与粒度在合理范围（默认单个计划不超过 30 个任务，单个任务预计不超过 45 分钟），超出时要求 lead 拆分或合并。
4. lead 认为需求不清楚时，把问题写进 `questions`，项目进入"等你回答"，用户在界面回答后 lead 重新规划。
5. **计划确认**：默认在界面展示任务图，用户可以确认、修改任务或重新生成，确认后才开始派发。设置中可改为"计划生成后直接开始"。
6. **执行中追加需求**：lead 做增量规划，只新增任务或修改尚未开始的任务；正在运行的任务不受影响，除非用户主动取消。

### 6.2 任务状态

```text
planned ─依赖全部合并─▶ ready ─派发─▶ running ─进程结束─▶ testing ─验证通过─▶ review ─评审通过─▶ integrating ─合并且测试通过─▶ merged
                           ▲            │                     │                  │                  │
                           └────────────┴──── 重试（带上失败原因，次数 +1）◀──────┴──────────────────┘
                                         重试用完 ─▶ blocked（交给 lead 处理）─▶ waiting-user（需要你决定）
任何状态 ─用户取消─▶ cancelled
```

| 状态 | 含义 | 谁推动 |
|---|---|---|
| planned | 依赖未完成 | 编排器 |
| ready | 可以派发，在队列中等运行槽 | 编排器 |
| running | 工具进程正在 worktree 中工作 | 开发 / 前端 |
| testing | 编排器运行验证命令；有独立测试角色时，先由它补测试 | 编排器 / 测试 |
| review | 评审工具审阅改动 | 评审 |
| integrating | 在集成队列中合并并跑项目测试 | 编排器 / lead |
| merged | 已进入 `ac/integration` | — |
| blocked | 自动重试已用完，lead 正在决定拆分、改派或调整验收 | lead |
| waiting-user | 只有用户能处理：登录、额度、预算、冲突、危险改动、需求问题 | 用户 |
| cancelled | 用户取消，已有改动保留在任务分支上 | 用户 |

每个任务默认最多 **3 次尝试**（含评审打回和集成失败回派），可在设置中修改。

### 6.3 派发

**提示词**由编排器生成，内容固定为：任务标题与说明、`plan.md` 中相关的接口约定、验收标准、`scope`、依赖任务的交付摘要、上一次尝试的失败原因（重试时），以及工作规则：

- 只修改 `scope` 内的文件；确需改动范围外的文件（如依赖清单），在最终答复中说明原因；
- 不要执行 `git commit`、`git push`、切换分支，不要修改 `.autocoder/`；
- 完成后用几句话总结做了什么、还有什么没做。

**无人值守参数**：每个工具在清单中增加以下字段，都可以在工具清单界面里编辑：

| 字段 | 作用 | 示例（以实际安装版本验证为准） |
|---|---|---|
| `auto_args` | 免确认、限定在工作目录内修改 | Claude Code 的权限模式参数，Codex 的工作区写入沙箱 + 不询问审批 |
| `stream_args` | 输出可解析的事件流，用于过程反馈 | Claude `--output-format stream-json`，Codex `--json` |
| `readonly_args` | 只读模式，用于规划和评审 | 只允许读文件的权限设置 |
| `auth_errors` / `limit_errors` | 识别"未登录"和"限流 / 额度用完"的输出关键字 | `not logged in`、`rate limit`、`429` |

**进程管理**：

- 工作目录固定为任务 worktree；标准输入直接关闭，工具一旦等待交互输入会立刻读到结束，而不是无限挂起；
- 输出写入 `~/.autocoder/logs/<project>/<task>/<attempt>.log`，不通过管道，这样 AutoCoder 重启后仍能继续读取；
- 每个进程放进独立的进程组（Windows 使用 Job Object），取消时整组结束，不留下子进程；
- 环境变量继承用户环境（工具才能用到各自的登录状态），另外注入 `AUTOCODER_TASK`、`AUTOCODER_PORT_BASE`（每个运行槽分配不同的端口段，避免并行测试抢端口）。

**并发**：全局运行槽默认 3、最多 5；每个工具同一时间只跑一个任务；按关键路径优先派发。某个工具被限流时只暂停这个工具，其他工具继续。

**改派**：任务优先给计划指定的工具。该工具不可用（未安装、停用、未登录、冷却中）时，交给承担同一角色的下一个工具；没有其他人承担这个角色时，交给 lead。

### 6.4 过程反馈

界面上看到的进度全部来自可观察的事实：

| 信号 | 来源 | 界面显示 |
|---|---|---|
| 是否在运行、已用时长 | 进程状态 | 运行槽、计时 |
| 正在做什么 | 事件流（支持的工具）或输出尾部 | 最近动作：读了哪个文件、改了哪个文件、跑了什么命令 |
| 改了多少 | 每 15 秒 `git status --porcelain` 和 `git diff --stat` | 改动文件数、增删行数 |
| 是否越界 | 改动文件与 `scope` 对比 | 越界警告 |
| 是否达标 | 验证命令结果、评审结论 | 验收标准逐条打勾、测试通过数 |
| 花了多少 | §7 计量 | token |

不显示无法核实的百分比，而是显示阶段：**已开始 → 改代码中 → 验证中 → 评审中 → 待合并 → 已合并**，再配合验收标准的完成数。

**卡住检测**：连续 10 分钟没有任何事件输出、也没有文件变化，判定为卡住；单次尝试超过 45 分钟判定为超时（两个时间都可设置）。两种情况都结束进程，已有改动作为 WIP 提交保留，再带上"上次停在哪里"重试。电脑睡眠造成的时间空档不计入。

**汇报记录**：每次尝试结束，编排器在 `.autocoder/reports/T3.md` 追加一条记录（时间、工具、退出码、工具的最终总结、改动统计、验证结果、token），界面的"进度汇报"时间线就来自这里。

**实时输出（随时看工具在干什么）**：每个运行中的工具进程都可以在界面上实时查看，不需要切到终端。

- **采集**：工具的标准输出和标准错误分别写进日志文件（§6.3），同时进入内存中的环形缓冲（每个进程保留最近 5000 行）。按行加序号和时间戳，标准错误单独标记。
- **两种视图**：
  - **动作**：从事件流解析出来的结构化记录，例如"读取 internal/order/state.go""修改 3 处""运行 go test ./internal/order/...（12 通过）""回复：……""用量 +3.2k token"。不支持事件流的工具从输出里识别常见模式，识别不了的原样显示。
  - **原始输出**：和在终端里直接运行时看到的一样，保留颜色（ANSI 转成样式），可以搜索、复制，可以跳到出错的行。
- **推送**：`GET /api/runs/{run}/stream` 使用 SSE。浏览器断线重连时带上最后收到的序号，从断点继续；序号已不在内存缓冲时从日志文件补齐。打开时先补发最近 200 行，再跟随实时输出。输出过快时每 100 毫秒合并发送一次，超长单行截断显示，完整内容仍在日志里。
- **入口**：
  - 侧栏"运行槽"中正在运行的格子，点击直接打开对应任务的输出；
  - 新增"运行监控"页，所有运行槽的输出并排显示，适合放在副屏上一直看；
  - 项目详情里的任务，运行中时详情面板直接显示实时输出，结束后显示每次尝试的完整日志。
- **状态栏**：每个输出面板顶部显示工具、任务、第几次尝试、已运行时长、距上次活动多久、改动文件数、本次 token。距上次活动超过 3 分钟变为黄色，达到卡住阈值（§6.4）变为红色。
- **操作**：只读查看，不能向工具输入内容（无人值守模式下也不应输入）。可以"停止"（结束进程组，改动保留为 WIP）或"停止并重试"。
- **脱敏**：输出在进入缓冲和日志之前，按常见密钥格式（API key、token、私钥头）替换为 `***`。
- **历史**：进程结束后，输出面板切换为该次尝试的日志，任务详情里可以查看每次尝试的日志。日志按项目保留最近 30 天或 1 GB，超出后自动清理最早的部分。

**提交由编排器完成**：尝试结束后，编排器在任务分支上提交改动，并写入可信的 trailer：

```text
feat(order): 实现订单状态机

AutoCoder-Task: T3
AutoCoder-Attempt: 2
AutoCoder-Tool: codex
AutoCoder-Verify: pass 12/12
AutoCoder-Tokens: 184230
```

如果工具不顾规则自己提交了，只要提交在任务分支上就保留，再补一个编排器的记录提交。

### 6.5 验证与评审

进程退出后，按顺序检查，任何一步不通过都带着具体原因进入下一次尝试：

1. **有没有产出**：没有任何改动视为失败（"分析"类任务除外）。如果工具的最终答复是在提问，转给 lead 回答；lead 也答不了，就转给用户。
2. **范围检查**：`scope` 之外的改动默认撤回并记录。依赖清单、锁文件、生成文件这类常见情况在项目设置中有白名单；对 `.autocoder/`、`.git/` 的改动一律撤回。
3. **危险改动**：删除文件超过 10 个、改动超过 2000 行，或改动 CI 配置、密钥、部署相关文件时，进入 `waiting-user`，由你确认。
4. **验证命令**：由编排器（不是工具）在 worktree 中运行任务的 `verify` 和项目的 `test_command`，有超时，结果写进汇报。
5. **补测试**：有独立的测试角色时，先派一个补测试的子任务到同一分支，再运行验证。
6. **评审**：评审工具在只读模式下看 diff 和验收标准，按固定格式给出结论（通过 / 需要修改 + 问题清单）。需要修改时，问题清单作为下一次尝试的输入。

### 6.6 集成与最终交付

**集成队列**：每个项目同一时间只合并一个任务，按依赖顺序在专用的集成 worktree 中进行：

1. 把任务分支以 `--no-ff` 合并到 `ac/integration`；
2. **有冲突**：撤销本次合并，在任务 worktree 中先合入最新的 `ac/integration`，把冲突文件和双方意图交给该任务的负责工具解决（解决不了再交给 lead），重新验证后再排队。冲突连续 2 次解决失败，转给用户，并列出冲突文件；
3. **合并后跑项目测试**：失败时把 `ac/integration` 退回合并前的位置（这是编排器独占的分支，可以安全回退），任务带上失败日志回派，原因标记为"与其他任务组合后失败"；
4. **疑似不稳定的测试**：失败后重跑一次，结果不一致的测试标记为"不稳定"写进汇报，不计为任务失败，但会在交付说明中列出。

**最终交付**（一个需求的全部任务合并后）：

1. 在 `ac/integration` 上运行完整的构建和测试；
2. 主分支在此期间有新提交（例如你手动改了代码）时，先把主分支合入集成分支，再测一遍；
3. lead 生成交付说明 `.autocoder/deliveries/R1.md`，内容包括：完成了什么、每条验收标准的结果、改动的模块、已知问题和不稳定测试、各工具的 token 用量；
4. **合并到主分支**：开启"自动合并"并且测试全部通过时直接合并；**项目没有可运行的测试时，即使开启了自动合并也会停下来等你确认**，因为"测试通过"这个条件无从判断；
5. 合并不碰你的工作目录：先在临时 worktree 中生成合并提交；你的主目录如果正检出主分支且没有未提交改动，就把它快进到合并结果；有未提交改动时，提示你先提交或暂存，再点"继续"；
6. 配置了远程仓库时可选推送并创建 PR。推送失败不影响本地交付，只在界面提示。

AutoCoder 只写 `ac/*` 分支和交付时的那一次主分支合并，从不强推，也不改写任何已有提交。

### 6.7 异常情况一览

| 类别 | 情况 | 如何发现 | 处理 |
|---|---|---|---|
| 工具 | 未安装、被停用、升级后参数失效 | 派发前检查；启动后几秒内报用法错误退出 | 标为不可派发，任务改派（§6.3），提示你到工具清单检查 |
| 工具 | 未登录、凭据过期 | 输出匹配 `auth_errors` | 暂停该工具的全部任务，提示你在终端登录，其他工具继续 |
| 工具 | 限流 / 额度用完 | 输出匹配 `limit_errors` | 该工具冷却（5 分钟起指数退避，最长 1 小时），任务排队或改派 |
| 工具 | 等待交互输入 | 标准输入已关闭 + 卡住检测 | 结束进程；同一工具连续发生，提示检查 `auto_args` |
| 执行 | 进程崩溃、非零退出 | 退出码 | 保存输出尾部，带上错误原因重试 |
| 执行 | 卡住、超时 | §6.4 | 结束进程，保留 WIP，重试；超时的任务提示 lead 拆小 |
| 产出 | 没有改动、只是在提问 | §6.5 第 1 步 | 失败重试；提问转给 lead 或你 |
| 产出 | 越界修改 | 改动与 `scope` 对比 | 撤回越界文件；白名单内的保留 |
| 产出 | 危险改动 | §6.5 第 3 步 | 等你确认 |
| 产出 | 验证失败、评审打回 | §6.5 | 带上日志或问题清单重试 |
| 产出 | 重试用完 | 尝试次数 | 交给 lead：拆分、改派或调整验收；lead 也处理不了就等你决定 |
| git | 合并冲突、合并后测试失败、不稳定测试 | §6.6 | 见 §6.6 |
| git | 你在主分支上有新提交或未提交改动 | 交付前检查 | 先合入主分支再测；未提交改动时等你处理 |
| git | 推送失败 | 退出码 | 保留本地结果，提示 |
| 计划 | 计划格式不合法、依赖成环、范围重叠 | §6.1 校验 | 交回 lead 重写，或自动串行化 |
| 计划 | 需求不清楚 | `questions` 非空 | 等你回答 |
| 环境 | 每个 worktree 需要装依赖 | 计划中的 `setup_command` | 创建 worktree 后先执行；失败时任务标为环境问题，等你处理 |
| 环境 | 并行测试抢端口 | 每个运行槽不同的 `AUTOCODER_PORT_BASE` | 预防为主 |
| 环境 | 磁盘空间不足 | 创建 worktree 前检查剩余空间 | 先清理已合并任务的 worktree，仍不足则暂停派发并提示 |
| 费用 | 超出项目 token 预算 | §7 实时累计 | 达到 80% 提醒，达到 100% 暂停派发并等你决定 |
| 费用 | 用量解析失败 | 解析器 | 按字符数估算并标注"估算" |
| 程序 | AutoCoder 崩溃、重启 | 启动时扫描运行记录（pid + 启动时间） | 进程还在就继续读日志、等它结束；进程已不在就按崩溃重试 |
| 程序 | 电脑睡眠 | 计时出现空档 | 空档不计入卡住和超时 |
| 程序 | 两个 AutoCoder 打开同一仓库 | `.git/autocoder.lock` | 第二个只能只读查看 |
| 用户 | 取消、暂停 | 界面操作 | 取消：结束进程组，改动留在任务分支；暂停：不再派发新任务，已在运行的跑完 |
| 用户 | 删除或停用了被分配的工具 | 清单变化 | 未开始的任务改派，正在运行的跑完 |
| 安全 | 输出中带出密钥 | 日志写入前按常见格式脱敏 | 完整日志只存在本机 `~/.autocoder/logs`，仓库里只保存摘要 |

### 6.8 你需要介入的时刻

默认只有这些时刻需要你，界面集中在"等你处理"列表中，每项都写明原因和可选操作：

1. 确认计划（可以关闭）；
2. 回答 lead 提出的需求问题；
3. 登录工具、额度用完或预算到了；
4. 危险改动确认；
5. 冲突连续解决失败，或 lead 也处理不了的任务；
6. 项目没有测试时的最终合并确认；你的主目录有未提交改动时的合并。

其余情况都由 AutoCoder 和 lead 自动处理，处理过程都记录在汇报时间线里。

## 7. Token 计量

所有工具消耗的 token 都要记录，并能看到明细。

### 7.1 采集方式

每次派发都会产生一条计量记录。编排器给命令追加清单中的 `usage_args`，让工具输出结构化结果，再从中解析用量：

| 工具 | 追加参数 | 用量来源 |
|---|---|---|
| Claude Code | `--output-format json` | 结果 JSON 中的 `usage`（输入、输出、缓存读写） |
| Codex CLI | `--json` | JSONL 事件流中的 token 统计 |
| Cursor Agent CLI | `--output-format json` | 结果 JSON 中的用量字段 |
| Gemini CLI / Qwen Code | `--output-format json` | 结果 JSON 中的统计字段 |
| 其他（Copilot CLI、OpenCode、Aider） | 无 | 按输入/输出字符数估算，记录标为"估算" |

各工具的字段名会随版本变化，M2 实现解析器时按实际安装版本逐一验证；解析失败时退回估算，而不是丢弃记录。

### 7.2 记录格式

```json
{"id":"r-0192","project":"shop-admin","task":"T3","tool":"codex","role":"developer",
 "start":"2026-10-15T08:04:11+08:00","duration_sec":83,"exit_code":0,
 "usage":{"input":35482,"output":4619,"cache_read":136467,"cache_write":12852},
 "estimated":false}
```

- 记录追加写入 `.autocoder/usage/<日期>.jsonl`。这个目录加入 `.gitignore`，避免每次调用都产生提交；里程碑合并时把汇总写进合并提交说明。
- 失败、超时、被取消的调用同样记录——它们也消耗了 token。
- lead 自己的规划、评审、集成调用也逐条记录，按角色区分。

### 7.3 展示

- **Token 用量**页：合计与输入/输出/缓存读写分项；按工具、按角色、按任务汇总；逐次调用的计量明细（时间、项目、任务、工具、角色、各分项、耗时、来源）；可按项目和工具筛选、导出 CSV。
- **项目详情**：项目总用量与各工具占比；任务详情显示该任务累计 token 与调用次数。

## 8. 系统架构

```text
┌─────────────────────────── autocoder（单个 Go 可执行文件）───────────────────────────┐
│  Web UI (Vue 3, go:embed)  ◀──HTTP/SSE──▶  API 服务                                   │
│                                              ├─ toolscan  工具清单与启动检测   ✅ 已实现 │
│                                              ├─ roles     角色分配             ✅ 已实现 │
│                                              ├─ settings  运行设置与角色分配     ✅ 已实现 │
│                                              ├─ project   项目/任务/汇报/计量文件 ✅ 已实现 │
│                                              ├─ gitops    分支/worktree/合并    ✅ 已实现 │
│                                              └─ dispatch  派发、观察、事件解析、   ✅ 已实现 │
│                                                 验证、集成、交付、用量解析               │
└──────────────────────────────────────────────────────────────────────────────────────┘
          │ exec                         │ exec                        │ exec
     claude -p "…"                  codex exec "…"                cursor-agent -p "…"
     (worktree T1)                  (worktree T3)                 (worktree T4)
```

技术选型理由：

- **Go 单文件**：纯 Go、`CGO_ENABLED=0`，一次构建出 macOS / Linux / Windows 全部产物，解压即用；调用本机 CLI 工具、操作 git、管理子进程都是 Go 的强项。
- **Vue 3 + Vite**：界面构建后通过 `go:embed` 打进二进制，默认只监听 `127.0.0.1:7788`。
- **只服务本机**：除默认监听 `127.0.0.1` 外，API 校验 Host 必须是回环地址（防 DNS 重绑定）；所有写请求必须带 `X-AutoCoder: 1` 头且 Origin 为本机，防止其他网页跨站修改工具清单。
- **git CLI 而不是 go-git**：worktree、merge 等行为与用户本机 git 完全一致，也能复用用户的凭据配置。
- 后续如需原生窗口，可在同一套前端上加 Wails 外壳，不影响核心逻辑。

### 8.1 桌面版与命令行版

功能都在 Go 程序里（调度、界面、API）。命令行版就是这个单文件；桌面版是一个 Rust（Tauri 2）外壳，把同一个 Go 程序作为内置引擎（sidecar）带在安装包里：

| | 命令行版 | 桌面版（`desktop/`，Rust + Tauri 2） |
|---|---|---|
| 启动 | 终端里运行，Ctrl+C 退出 | 双击打开，自己的窗口里显示界面；菜单栏（Windows 任务栏通知区、Linux 状态栏）出现图标 |
| 关掉界面 | 关浏览器，服务继续运行（终端还开着时） | 关窗口只是隐藏，派发在后台继续；macOS 上窗口藏起来后 Dock 图标也收起，只留菜单栏图标 |
| 日志 | 终端 | `~/.autocoder/autocoder.log`（超过 10 MB 轮换一次） |
| PATH | 继承终端 | 从访达或桌面菜单打开时只有系统默认 PATH，引擎启动时读一次登录 shell 的 PATH 合并进来，才能找到 Homebrew、npm、nvm 装的工具 |
| 产物 | 6 个平台的单文件，`CGO_ENABLED=0` 交叉编译 | macOS（Apple 芯片、Intel 各一个 dmg）、Windows（安装程序 exe 和 msi）、Linux（AppImage 和 deb），各在自己的系统上封装 |

外壳和引擎的分工：

- 外壳启动时先看 `127.0.0.1:7788` 上是否已经是 AutoCoder（比如命令行版在跑）：是就直接用它；否则以 `autocoder --desktop serve` 启动内置引擎，等 `/api/version` 就绪后在窗口里打开界面。引擎没能启动时窗口里显示原因和日志位置。
- 菜单栏内容由引擎生成（`internal/tray`），外壳每 2 秒取一次 `GET /api/desktop/menu`，图标取 `GET /api/desktop/icon.png`；暂停 / 恢复用 `POST /api/desktop/pause`，退出用 `POST /api/desktop/quit`。这几个接口要求请求头带外壳启动引擎时随机生成的令牌（环境变量 `AUTOCODER_DESKTOP_TOKEN`，引擎读到后从环境里删掉，不传给开发工具），本机其他程序和网页不能借此让 AutoCoder 退出。
- 界面里在新窗口打开的链接（GitHub、尝试日志）和窗口外的网址用系统浏览器打开，窗口里只显示 AutoCoder 自己的页面。
- 再次打开 AutoCoder 不会起第二个，只把已有窗口拿到前面。
- 外壳意外结束时引擎的标准输入会关闭，引擎照常收尾退出，不会留在后台。

菜单栏菜单：

- 第一行：`运行中 2 / 3`、`空闲 · 3 个运行槽` 或 `已暂停派发`；macOS 图标旁显示运行中的数量。
- 正在运行的尝试，最多 5 行：`T2 商品列表页 · Codex CLI 评审中 · shop-admin`，点开对应项目页。
- 等你处理：受阻和等你确认的任务、待回答的问题、待确认的计划、规划失败、预算用完，最多 5 行，点开对应项目页。
- 今日用量与调用次数，以及按工具的分项。
- 打开 AutoCoder、暂停 / 恢复派发、退出。Windows、Linux 上左键单击图标直接打开窗口。

图标由程序绘制：几个竖条表示运行槽，忙的实心、空的描边；有事等你处理时右上角加圆点，暂停时变淡。macOS 用模板图标，随菜单栏深浅自动着色。

退出（菜单栏"退出"、Command-Q、Ctrl+C 或 SIGTERM）时停止派发，结束正在运行的工具进程：已有改动作为 WIP 提交保留，任务放回队列且这次不计入尝试次数，规划和评审下次启动重新做；引擎最多等 20 秒，外壳最多等 30 秒。

发布由 `.github/workflows/release.yml` 完成：Linux 上交叉编译 6 个平台的命令行版，再在 macOS、Windows、Linux 机器上把对应的命令行版放进外壳（`desktop/src-tauri/binaries/autocoder-engine-<目标三元组>`）封装成安装包，最后统一生成 `SHA256SUMS.txt`。署名 M&J Group；Windows msi 用 `desktop/src-tauri/wix/main.wxs`（Tauri 默认模板，厂商名在 XML 里写成 `M&amp;J Group`，因为 Tauri 填模板时不转义）。Windows 安装包内置 WebView2 离线安装程序，没有网络也能装。

还没有的：Apple 开发者证书签名与公证（现在是临时签名，第一次打开要右键选择"打开"）、Windows 代码签名、应用内自动升级、界面多语言。

### 10.1 当前实现与设计的差异

- `.autocoder/` 的读写在集成 worktree（`<仓库上级>/.ac-worktrees/<项目>/_integration`）里进行，并提交到 `ac/integration`，交付时随合并进入主分支；你的工作目录在交付前不会出现任何 AutoCoder 写入的文件。
- 工具输出目前通过管道读取并同时写入日志文件；AutoCoder 重启时正在运行的任务按"被中断"放回队列重试，还不会重新接上仍在运行的进程。
- Windows 上用 `taskkill /T` 结束进程树，尚未使用 Job Object；原始输出暂不保留 ANSI 颜色。
- 同一仓库被两个 AutoCoder 打开的锁（`.git/autocoder.lock`）、日志按 30 天 / 1 GB 清理尚未实现。
- §6.5 第 5 步（有测试角色时先派补测试的子任务）尚未实现；测试角色目前只承担计划中 `role: tester` 的任务。
- 重试用完的任务停在"受阻"等你处理，还不会先交给 lead 拆分或改派；工具在提问时同样直接重试，不转给 lead 回答。
- 规划在 `<仓库上级>/.ac-worktrees/<项目>/_plan` 这个与集成分支一致的分离 worktree 中进行，每次规划前后都会丢弃其中的改动；计划保存在 `.autocoder/requests/R<n>.yaml`，给人看的版本在 `.autocoder/plans/R<n>.md`。
- 评审接在同一次尝试的输出和日志后面；评审尽量交给不是作者的工具，别的评审工具只是在忙时会等它，只有没有别的工具可用时才由作者自审。评审结论无法解析时重新评审一次，仍无法解析按通过处理并在汇报中注明。
- token 预算按项目设置：用到 80% 在项目页提醒，用完后这个项目不再派发新任务和规划，正在运行的跑完。
- 菜单栏图标在 Linux 上用 StatusNotifierItem（D-Bus），GNOME 需要装 AppIndicator 扩展才显示；没有托盘时服务照常运行，只是没有图标。macOS 和 Windows 的菜单还没在真机上看过，只确认了能编译（macOS 由 CI 在 Mac 上编译）。
- 各工具 `auto_args` 等参数的默认值按常见版本填写，未在每个工具的最新版本上逐一验证；可在工具清单界面修改。

## 11. 已确认的决定

| 问题 | 决定 |
|---|---|
| 费用 / token | 记录全部工具的全部 token 消耗，提供计量明细（§7） |
| 合并到主分支 | 集成测试通过后由项目管理直接合并，默认不等确认（可在设置中关闭）；项目没有可运行的测试时仍会等你确认 |
| 并发上限 | 默认同时运行 3 个工具进程，最多 5 个 |
| IDE 工具 | 统一只用 CLI 工具，便于派发、管理和计量 |
| 工具清单管理 | 全部在界面上完成，不要求用户修改配置文件 |
| 添加项目 | 优先读取本机 git / gh 账号列出仓库，像 Claude Code 一样点选添加 |
| 过程反馈 | 以可观察的事实（进程、事件流、改动、验证结果）为准，提交由编排器完成，不依赖工具按约定自述（§6） |
